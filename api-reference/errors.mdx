The Ecosystem API uses standard HTTP status codes and a consistent JSON error response body to communicate what went wrong and how to fix it. Every error response — regardless of the error type — follows the same structure, so you can handle failures uniformly in your integration code without special-casing each endpoint.

## Error Response Format

When a request fails, the API returns a JSON object with a top-level `error` key. The object always includes a machine-readable `code` and a human-readable `message`. For validation failures, it also includes a `details` array that pinpoints the specific fields that failed.

```json
{
  "error": {
    "code": "validation_error",
    "message": "Human-readable description of what went wrong.",
    "details": [
      { "field": "customer.contact_email", "issue": "must be a valid email address" }
    ]
  }
}
```

<ResponseField name="error.code" type="string" required>
  A stable, machine-readable identifier for the error type (e.g., `"validation_error"`). Use this field — not the HTTP status code alone — to branch your error-handling logic. Codes will not change between API versions.
</ResponseField>

<ResponseField name="error.message" type="string" required>
  A human-readable sentence describing what went wrong. Intended for logging and debugging — do not display this string directly to end users, as the wording may change without notice.
</ResponseField>

<ResponseField name="error.details" type="array">
  An optional array of objects present when the error involves one or more specific fields (e.g., validation errors). Each item in the array contains a `field` path (dot-notation) and an `issue` string describing the problem with that field.

  <Expandable title="details item fields">
    <ResponseField name="field" type="string">
      Dot-notation path to the field that caused the error (e.g., `"customer.contact_email"`, `"location.zip"`).
    </ResponseField>
    <ResponseField name="issue" type="string">
      A short description of the validation failure for that field (e.g., `"must be a valid email address"`, `"is required"`).
    </ResponseField>
  </Expandable>
</ResponseField>

## HTTP Status Codes

The following table lists every HTTP status code the API can return, what it means in the context of the Ecosystem API, and the general action you should take.

| Status | Name | When It Occurs |
|---|---|---|
| `200` | OK | Successful `GET` or `PATCH` request. The response body contains the requested or updated resource. |
| `201` | Created | Successful `POST` request. The response body contains the newly created resource, including its assigned `id`. |
| `400` | Bad Request | The request body contains malformed JSON or uses invalid syntax. Fix the payload before retrying. |
| `401` | Unauthorized | The `Authorization` header is missing, the token is malformed, or the token has been revoked. |
| `403` | Forbidden | The token is valid, but the authenticated account is not permitted to perform this action. |
| `404` | Not Found | The requested resource does not exist, or you do not have permission to know it exists. |
| `409` | Conflict | A duplicate resource was detected (e.g., an opportunity with the same customer and location already exists). |
| `422` | Unprocessable Entity | The JSON is syntactically valid, but one or more field values failed business-logic validation. Check `error.details`. |
| `429` | Too Many Requests | You have exceeded the rate limit of 300 requests per minute. Wait and retry after the `Retry-After` interval. |
| `500` | Internal Server Error | An unexpected error occurred on the Rhombus servers. Retry with backoff; contact support if the error persists. |

<Note>
  `400` and `422` are distinct: a `400` means the request could not be parsed at all, while a `422` means the server understood the request but rejected specific values. Always check for `422` with a `details` array when debugging data submission issues.
</Note>

## Error Codes Reference

Use the accordions below to look up a specific error code, understand what triggers it, and learn how to resolve it.

<Accordion title="Authentication errors: missing_token, invalid_token, revoked_token">
  These errors all return `401 Unauthorized` and indicate that the request could not be authenticated.

  | Code | Cause | Resolution |
  |---|---|---|
  | `missing_token` | The `Authorization` header was not included in the request. | Add `Authorization: Bearer <your-api-key>` to every request. |
  | `invalid_token` | The token is malformed (e.g., truncated, contains invalid characters) or does not match any key in the system. | Verify you copied the full key from **Settings > API Keys**. Regenerate if necessary. |
  | `revoked_token` | The key was explicitly revoked via the portal or the API. | Generate a new API key in **Settings > API Keys** and update your integration. |

  ```json
  {
    "error": {
      "code": "revoked_token",
      "message": "This API key has been revoked and can no longer be used."
    }
  }
  ```
</Accordion>

<Accordion title="Validation error: validation_error">
  Returns `422 Unprocessable Entity`. One or more fields in the submitted payload failed validation. This is the most common error when creating or updating opportunities.

  The `details` array will contain one entry per failing field. Iterate over it to surface all problems at once rather than fixing them one at a time.

  ```json
  {
    "error": {
      "code": "validation_error",
      "message": "The submitted data contains validation errors.",
      "details": [
        { "field": "customer.contact_email", "issue": "must be a valid email address" },
        { "field": "location.zip", "issue": "must be a 5-digit US ZIP code" }
      ]
    }
  }
  ```

  **Resolution:** Inspect each item in `details`, correct the corresponding fields in your payload, and resubmit.
</Accordion>

<Accordion title="Missing field error: missing_required_field">
  Returns `422 Unprocessable Entity`. A field marked as required in the API schema was not present in the request body. This is distinct from `validation_error`, which applies to fields that were provided but contain invalid values.

  ```json
  {
    "error": {
      "code": "missing_required_field",
      "message": "One or more required fields were not provided.",
      "details": [
        { "field": "customer.company_name", "issue": "is required" }
      ]
    }
  }
  ```

  **Resolution:** Review the endpoint's parameter documentation to identify all required fields. Add the missing fields to your payload and retry.
</Accordion>

<Accordion title="Duplicate opportunity error: duplicate_opportunity">
  Returns `409 Conflict`. An opportunity with the same customer and location combination already exists in the system under your partner account. Rhombus de-duplicates on `customer.company_name` + `location.address` + `location.zip`.

  The `details` array will include the `id` of the existing opportunity so you can retrieve or update it instead of creating a new one.

  ```json
  {
    "error": {
      "code": "duplicate_opportunity",
      "message": "An opportunity for this customer at this location already exists.",
      "details": [
        { "field": "id", "issue": "opp_4f8c2a1b3e" }
      ]
    }
  }
  ```

  **Resolution:** Use the returned `id` to fetch the existing opportunity via `GET /opportunities/{id}`. If the existing record needs updates, use `PATCH /opportunities/{id}` rather than creating a duplicate.
</Accordion>

<Accordion title="Not found error: not_found">
  Returns `404 Not Found`. The resource identified by the URL path does not exist, or it exists but is not visible to your partner account.

  ```json
  {
    "error": {
      "code": "not_found",
      "message": "The requested resource does not exist."
    }
  }
  ```

  **Resolution:** Verify the `id` or path segment in your request URL. Confirm the resource was created successfully and belongs to your partner account.
</Accordion>

<Accordion title="Rate limit error: rate_limit_exceeded">
  Returns `429 Too Many Requests`. Your API key has sent more than 300 requests within the current one-minute window.

  The response includes a `Retry-After` header with the number of seconds to wait before the window resets, as well as the standard `X-RateLimit-*` headers.

  ```json
  {
    "error": {
      "code": "rate_limit_exceeded",
      "message": "You have exceeded the rate limit. Please slow down and retry after the indicated delay."
    }
  }
  ```

  **Resolution:** Pause your request loop for the number of seconds in the `Retry-After` header. If you consistently hit this limit, consider batching requests or distributing load across time. See [Retry Strategy](#retry-strategy) below for a code example.
</Accordion>

<Accordion title="Internal server error: internal_error">
  Returns `500 Internal Server Error`. An unexpected error occurred on the Rhombus servers. This is not caused by anything in your request, but you should not flood the server with retries.

  ```json
  {
    "error": {
      "code": "internal_error",
      "message": "An unexpected error occurred. Please try again later."
    }
  }
  ```

  **Resolution:** Retry the request using exponential backoff (see [Retry Strategy](#retry-strategy) below). If the error persists across multiple retries or affects production workflows, contact Rhombus partner support and include the request timestamp and any `X-Request-Id` response header value.
</Accordion>

## Retry Strategy

Implement exponential backoff with jitter for `429 Too Many Requests` and `500 Internal Server Error` responses. This prevents thundering-herd problems where many clients retry simultaneously and worsen a temporary overload. For `429` errors specifically, always respect the `Retry-After` header as a floor — do not retry sooner than its value regardless of your backoff calculation.

The following JavaScript utility wraps any `fetch` call with automatic retries:

```javascript
/**
 * Retries a fetch request with exponential backoff for 429 and 500 errors.
 * @param {string} url - The endpoint URL.
 * @param {RequestInit} options - Fetch options (method, headers, body, etc.).
 * @param {number} maxRetries - Maximum number of retry attempts (default: 4).
 * @returns {Promise<Response>} - Resolves with the successful response.
 */
async function fetchWithRetry(url, options = {}, maxRetries = 4) {
  const RETRYABLE_STATUSES = new Set([429, 500]);
  const BASE_DELAY_MS = 500; // starting backoff in milliseconds

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (!RETRYABLE_STATUSES.has(response.status)) {
      // Success or a non-retryable error (4xx) — return immediately.
      return response;
    }

    if (attempt === maxRetries) {
      // Exhausted all retries — surface the last response.
      return response;
    }

    // Respect Retry-After for 429; otherwise use exponential backoff with jitter.
    let delayMs;
    if (response.status === 429) {
      const retryAfter = response.headers.get("Retry-After");
      delayMs = retryAfter
        ? parseInt(retryAfter, 10) * 1000
        : BASE_DELAY_MS * 2 ** attempt;
    } else {
      // Exponential backoff: 500ms, 1s, 2s, 4s … plus up to 200ms random jitter.
      delayMs = BASE_DELAY_MS * 2 ** attempt + Math.random() * 200;
    }

    console.warn(
      `Request to ${url} returned ${response.status}. ` +
      `Retrying in ${Math.round(delayMs)}ms (attempt ${attempt + 1} of ${maxRetries}).`
    );

    await new Promise((resolve) => setTimeout(resolve, delayMs));
  }
}
```

<Tip>
  Log the `X-Request-Id` response header on every request. If you need to open a support ticket for a `500` error, providing this ID allows the Rhombus team to trace the exact server-side execution without requiring you to reproduce the issue.
</Tip>
